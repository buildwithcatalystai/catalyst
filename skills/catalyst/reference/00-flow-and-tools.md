# Flow & tools — transitions, lifecycle, and the per-employee surfaces

> **What this is.** SKILL.md teaches *judgment* and names who's on the work (the Analyst, the PM, the Engineer); it deliberately doesn't list tools. This file is the operational map — the **transition** tools that bring in each employee, the **lifecycle** tools that work with anyone on it, and which **work surface** each employee unlocks. The live MCP schemas (name / args / description) always reach you at call time; reach for this when you need the at-a-glance "what brings in whom."
>
> **Internal map (never said to the user):** the Analyst = `start_analysis` (Discover mode), the PM = `start_spec` (Spec mode), the Engineer = `start_app_building` (Build mode). Both the stage words and the employee names stay in the mechanics (2026-10-14): to your companion there is only you, one Wingman.

## Transitions — shift gears

You never track who's on it yourself; you call a transition and the stance follows. Nothing is denied by gear (since 2026-10-14) — the discipline below is yours to keep.

All three gears work the ONE `coding_workspace__*` surface, whole, plus every native tool. A gear changes how you work, not what you may touch.

| Transition | Brings in | Notes |
|---|---|---|
| `start_analysis(prompt?)` | **the Analyst** | Investigate the business from its real data — get to the bottom of the problem with `run_select_query` / `run_python` / the knowledge base. **Acts on your CURRENT Mindspace** (the plugin fills the id; you don't pass it). **Discipline, not a deny:** the Analyst changes nothing and ships nothing — no `write`/`edit`/`playwright`/`save_prd` while investigating, even though every tool is open (the *Mindspace* persists; see below). `coding_workspace__bash` stores your working plan in the Mindspace; native `Agent` fans out a parallel survey. Close by *recommending* the path forward (options, pros/cons, your pick) — never "what next?". |
| `start_spec(prompt?)` | **the PM** | Shape build-ready PRDs *with the user*, in conversation. Author each PRD, write it with `save_prd` (many accumulate in the PRD folder; each lands on the companion's list as one `prd` task), then **track every outcome** — one task per Requirements row in the org's project-management tool, stamped with the Mindspace id + PRD id, the IDs written back into the PRD. **Acts on your CURRENT Mindspace.** **Discipline, not a deny:** the PM shapes and doesn't build — no build actions (`write`/`edit`/`bash`/`playwright`) while planning; `save_prd` is the PM's hand. |
| `start_app_building(prompt?, app_name?)` | **the Engineer** | Make whatever the problem needs and prove it runs — from a clear ask, or a PRD the user aimed at the Hive. **Acts on your CURRENT Mindspace** (same id across employees). Scaffolds on first web-build. Pass the ask (or the PRD direction) as `prompt`. The app lives on the workspace: its files go through `coding_workspace__*`, never native `Write`/`Edit` (those act on the laptop). To build a *different* existing Mindspace, `switch_mindspace` to it first. |

**One Mindspace, many hands — the transition always means the one you're in.** `start_analysis` / `start_spec` / `start_app_building` bring an employee onto *your current Mindspace* (same id, same data, findings carry forward). **You don't supply or track the id — every Catalyst tool auto-targets your current Mindspace** (the plugin stamps it from your *local* sentinel into the call; any `session_id` you set is overwritten). This is true for *all* of them — transitions, `coding_workspace__*`, `current_session`, recall — not just the transitions. A transition can therefore never fork or jump. **Changing *which* Mindspace is `switch_mindspace`'s job — by name, in the background, with a one-line receipt:** `switch_mindspace(target='<name>')` to pick up a *different* existing one (the server resolves the name; you never type an id you weren't handed), or `switch_mindspace()` (clean slate) to start a fresh one — then the next transition continues whatever switch left active. It asks first only when the current Mindspace has work in flight.

**The no-write limit is the *Analyst*, NOT the Mindspace.** The Analyst denies the write/build *tools* — but the Mindspace is NOT disposable: its findings, `mindspace_memory`, and `mindspace_skill` persist and are the *seed* for the PM/Engineer on the SAME Mindspace. Never reason "the Analyst changes nothing → nothing to lose → switch away" — that strands the findings. You carry the investigation *forward* into the same Mindspace's build; you don't abandon it.

**The three employees are ONE arc — hand forward, you can't fork.** As the work moves understand → plan → make on the effort in front of you, just call the next transition — it continues the SAME Mindspace (the plugin keeps the id). An app built from what the Analyst just found is the *same effort*; keep going. The only way to leave the current effort is **`switch_mindspace`** — to a different existing Mindspace by name, or `switch_mindspace()` for a clean slate (a fresh one). Both move in the background with a one-line receipt, confirmed only when the current Mindspace has work in flight (a build the Engineer is on, a Spec Q&A that rewinds) — and you literally can't do it by accident through a transition.

**Which tool for what.** The Catalyst tools are the company's hands — `run_select_query` / `run_python` / the knowledge base for its data, `coding_workspace__*` for anything on the workspace (the app, the Mindspace's files). Native file/shell tools act on your companion's own machine; external MCP servers are theirs too. All of them are open in every gear (2026-10-14) — reach for the one that touches the right place.

## Lifecycle — employee-agnostic, safe from any tab

| Tool | Purpose |
|---|---|
| `open_scratchpad` | **The landing call — your first and only call on every `/catalyst` activation.** Auth probe + opens the caller's ScratchPad with the Analyst live, one hop, no args. `authenticated:false` → read `message`, do it, stop; `status:error` → read `fix_required`; ok → greet — `persona_status: 'new'` is a **first meeting**, greet it as one by `user_name` (warm, one line on who you are, then what they're on); otherwise *"Welcome back, <name>"* — (+ their ToDos' one line from `digest`) + "What's on your mind?"; relay `todos_block`; `persona_block` is their working model — read before anything of substance. Also here: `directory_block` (where the Company Directory places them, who is around them — read, never recite), `mindspace_of_interest` (the Mindspace they last worked in — pick it up by name the moment their first message is about it) and `firsts` (counts of own Mindspaces, shares — a zero means that first is still ahead; teach it in one line when it happens). Built lean — auth, the ScratchPad, their ToDos, these three, nothing else. |
| `ensure_auth` / `logout` | The auth gate for the `/catalyst status|list|end` commands and reauth checks — NOT a landing step (`open_scratchpad` probes auth itself). `logout` signs out; read its `message` verbatim. |
| `health_check` | On-demand diagnostic when `open_scratchpad` or a workspace tool errors; `ready_to_build: false` → read `fix_required` to the user and stop. Never on landing. |
| `list_mindspaces` | The shelf — ONLY when the user asks to see or pick from their Mindspaces. Render with full session_ids, never truncated; show the phase in plain words (exploring / planning / building / shipped) — never a role name. |
| `current_session` | "Who's on it right now?" → `{active, session_id}` for your current Mindspace (the plugin fills the id). Safe from any tab; a tab with nothing active gets `{active: false}`. |
| `switch_mindspace(target?, confirm_clear_current?)` | **Non-destructive** pick-up or clean slate — the primitive for "pick up <name>" / "step away" / "build new". `target` = the name as the user says it (slug or a handed id also work), resolved server-side over yours ∪ shared-for-editing; `not_found` carries the candidates — ask which, never guess; `read_only` = a colleague's trusted Mindspace (read it via `read_org_skill`). A background mechanic with a one-line receipt. It returns `needs_confirm_clear_current` only when the current Mindspace has work in flight (a build the Engineer is on; a graph Spec Q&A, which rewinds a question or two): relay it, then re-call with `confirm_clear_current=true` only on a clear yes. |
| `abandon_build(reason?)` (alias `end`) | Destructive — wipes local session state + marks the row abandoned. Works from any tab. Resurrectable. Only on an explicit "end / abandon / kill it." |
| `complete_build(summary)` | Finalize a build after the completion JSON — runs migrations, boots the dev servers, returns the URLs. Idempotent (a Stop hook also fires it as a safety net). |
| `mindspace_skill(mode)` | THIS Mindspace's durable skill (how the area works) — a detailed core doc + references. Read on entry; `write_skill` to grow the core doc, write a reference for depth, as you learn. (Bound while the Analyst or Engineer is on it.) |
| `todos(mode)` | The shared ToDo list — one per company, filtered by person and by Mindspace. `list` (mine · asked · mindspace · open) · `create` (assignee = a NAME or email, or `me`; a name not on Catalyst still works — it links when they join) · `answer` (assignee only) · `update` · `close` (requester only) · `comment` · `people`. The landing and every Mindspace entry carry `digest` + `todos_block` — relay, then act. Detail: `reference/10-todos.md`. |
| `mindspace_memory(mode)` | THIS Mindspace's living memory — discrete facts you'd look up (not understanding; that's the skill). Recall on entry; save the moment you learn. (Bound while the Analyst or Engineer is on it.) |

## Work surface — one surface, every gear has all of it

There is ONE bound surface, `coding_workspace__*` (the FDE union), and every gear carries the whole of it plus every native tool. What differs is what each gear *reaches for*:

- **The Analyst** — `read` / `grep` / `find`, the DB + API knowledge base, `run_select_query`, `run_python` (pandas + a read-only `query(sql)→DataFrame`, state persisting across calls), `coding_workspace__bash` (so the working plan persists in the Mindspace), native `Agent` for a parallel survey. By discipline it does not `write` / `edit` / `playwright_test` / `save_prd` — it investigates, it doesn't make; **never a web app**.
- **The PM** — the same, **plus `save_prd`** to author build-ready PRDs and `todos` to put each PRD on the shared ToDo list and track it to done. By discipline no build actions while planning.
- **The Engineer** — read / write / edit / bash / grep / find, `get_prd` (the contract), `get_repo_map` (daemon-fresh index), `run_python`, `run_select_query`, `playwright_test` (the one validation tool), **plus the automation families — jobs, scheduled jobs, subagents (autonomous AI checks), triggers.** A script, job, AI check, ML model, or web app all build here — on the workspace, through `coding_workspace__*`.

Every gear also exposes the user's **connected external tools** (discover → execute), `mindspace_skill` / `mindspace_memory`, and their own external MCP servers.

Full per-tool catalog → `05-tools.md`.

## Status (the MCP writes it; you read it only for sanity)

Internal status flows `spec → db_finalize → generate → completed`. Treat `{completed, error, abandoned, generate-interrupted}` as equivalent — same actions available, nothing terminal. (Surface it to the user only in plain words — exploring / planning / building / shipped — never the raw status word, never a role name.)
