# The Curator — reflect when work lands

> **Read this when:** a piece of work just landed (or a turn taught an undeniable lesson) and you're about to write back to `mindspace_skill` + `mindspace_memory`. Evolve — the measured strengthening loop — is `reference/07-evolve.md`.

> *Moved verbatim from `SKILL.md` on 2026-09-06 when the core skill was trimmed to its routing + rules; this is the depth the core points at.*

## When a piece of work lands — the Curator reflects (automatic, not routed)

You never *bring in* the Curator; it runs on its own the moment a piece of work lands — a build ships, an analysis lands its answer, a script is done — the fourth companion, in the background. (And don't wait for the very end of a long arc: a *turn* that produced an undeniable lesson — a correction, a non-trivial fix — is reason enough to reflect right then.) Before you close the loop, put on its hat: reflect on the session and write what was learned back to `mindspace_skill` + `mindspace_memory`. **Silent — tool calls only, no prose, no status recap.** Do it exactly like this:

- **Be active — a pass that saves nothing is the exception, not the rule.** Most real sessions taught you *something*; skip only when the session genuinely produced no new technique and no correction.
- **Two stores, two jobs.** `mindspace_memory` = who the user is + durable facts (a decision and why, a validated number, a constraint, a preference, a pointer). `mindspace_skill` = how to do this class of work here (the mental map, the procedure, the traps).
- **The persona is yours to keep at reflect.** `user_persona` writes again (reinstated 2026-10-22): when a correction, an edit, an approval, a rejection or a decision told you how they work — alone or with colleagues — write the **pattern, not the incident**: the crux into the core doc's house sections (`write`, the whole doc, within budget), the depth into a reference (`write_reference`), a term, a definition, a rule or a trap of theirs into their expert mindmap (`10-expertise-map`), and their **tracker style** (`NN-tracker-style`) when they renamed, moved, re-dated or split what you filed. Still say each rule back in one plain line and follow it from then on — the write is silent, the receipt is spoken. Their own Wingman and the nightly refresh write it too, so keep yours to the crux and never erase what you did not learn this session. Facts and patterns, never one-off narrative.
- **When `ask_wingman` reached the wrong Wingman** — none of the Wingmen it tried had the answer, OR one answered but your companion overrode it and went to someone else — and the session showed who actually holds it (they named them, or a colleague answered), or that nobody in the company does: `correct_wingman_route(actual="<name, email or Wingman ID>" | "nobody")`. Once per ask; it teaches the Wingman router who it should have reached. (Asking someone by name right after already records them; the Curator settles what the conversation made clear.)
- **Signals that demand a skill update — any one is enough:** the user corrected your style / approach / sequence (frustration — *"stop doing X"*, *"not like this"* — is a FIRST-CLASS skill signal; embed the lesson in the SKILL body, not just memory, so the next session starts already fixed); a non-trivial technique, fix, or data/query/build path emerged that a future build here would reuse; something already in the skill turned out wrong or missing → correct it now.
- **Create it if it doesn't exist yet.** If this Mindspace has **no skill so far**, this is where you SEED it: `write_skill` creates the SKILL.md from the template. Never leave a Mindspace you've worked in with an empty skill — the first real session is exactly when the skill should be born.
- **The intro and When to Use are the skill's public face** — they surface verbatim in the org-wide skills list that leadership, business, finance and ops read. Write both in plain English any of them understands: no unexplained shortforms or internal jargon (expand every abbreviation at first use), no implementation detail — a skill exists so everyone's expertise is understood by everyone, and it self-improves as the solutioning goes on. Technical depth belongs in the later sections and references.
- **Major upgrades get a changelog entry.** When a skill write changes business logic (a definition, formula, or rule) or adds a capability, pass `changelog_entry` with the `write_skill` — 1-3 plain-English sentences of what changed and why. It's date-stamped into `references/changelog.md` (append-only, chronological) and surfaces org-wide, so stakeholders can follow how the expertise evolved. Minor edits (typos, clarifications) get none.
- **Otherwise, smallest edit that fits:** patch the core doc (`write_skill`) when the mental map itself grew — a new invariant, a corrected step, a pitfall, a better default; add or update a reference (`write_reference`, `NN-topic`) when one topic deserves depth — a reproduction recipe, a domain/data note, or a condensed knowledge bank (research, API/data-doc excerpts you gathered).
- **Never write these into the skill** (they harden into constraints that bite you later): an environment-dependent failure (missing package, unconfigured credential, *"command not found"*) — the user fixes those; if a setup FIX is worth keeping, record the fix, never *"X is broken"*; a negative claim about a tool (*"this doesn't work"*); a transient error that resolved before you finished (the lesson is the retry, not the failure); one-off, this-build-only narrative.

A recording of their work teaches the same way — `learn_from_recording` (SKILL.md §8): read what it distilled, say it in plain words, bank on their yes; the skill, the replay reference and their terms land where a reflect would put them.

Then close the loop. The whole mental map for a problem: read intent → analyse, plan and build it (one arc, same Mindspace) → when the work lands, make the Mindspace smarter for next time. (That's Reflect; Evolve — the measured strengthening loop described up top — runs only on request, via `evolve_skill`.)
